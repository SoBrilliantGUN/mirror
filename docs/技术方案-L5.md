# 技术方案 · L5 状态与会话（具体实现）

> 从 `技术方案.md` §三 L5 行拆出。**状态 = 每通电话内的内存态（每通全新开始）**；
> **时间感知 = 通话内被动感知（不推送、不调度）**；**记忆 = 已实现，作综述接入**。
>
> 已锁定的边界：**MBTI 画像丢弃**，不写、不设计、不埋缝（原 `MBTIProfile` 空接口一并删除）。

---

## 一、目标与边界

**要解决**：L5 是「会话状态 + 时间感知」这一层。会话状态（mode / mood 情绪轨迹 / 本轮上下文 /
对话历史 / V0 人格）当前散在 `server.ts` 的模块级变量里，逻辑是对的但没有一个成文契约；时间感知
目前是空接口（`contracts` 里的 `TimeAware {}`），没实现。

**L5 做什么**：

1. 把「会话状态」收敛成一个清晰的**生命周期契约**：每个状态属于谁、何时诞生、何时清零。
2. 把 `TimeAware` 从空接口填成真实现：**时间上下文注入 + 重要日期记忆 + 作息关怀**（三层都只在通话内被动体现）。
3. 定义**时间锚点（TimeAnchor）数据模型**：记忆里的时间只能是**绝对时间**或**周期时间**，禁止相对时间。

**L5 不做什么**（边界）：

- **不跨通话持久化 mood / mode**（每通全新开始；跨通话连续性交给长期记忆的 episodic / fact / insight）。
- **不做通话外主动推送 / 定时调度**（产品形态是「用户主动打进 / 挂断」，无推送通道，不新增基础设施）。
- **不新建独立「日期表」**：重要日期复用 `memories` 表，挂时间锚点字段，走同一条记忆通路。
- **不做 MBTI 边聊边读**（丢弃）。
- **不引入农历换算库**（V0 只支持公历周期；农历是 schema 里预留的后续类型）。

## 二、会话状态（内存态 + 生命周期）

### 2.1 状态清单

会话状态是**每通电话内的内存态**，全部落在 `server.ts`（当前）或将来的一处 `SessionState` 聚合（建议）：

| 状态 | 类型 | 载体 | 归属 | 每通是否清零 |
|---|---|---|---|---|
| mode（闲聊 / 小心翼翼） | `Mode` | `ModeTracker`（`brain/modeTracker.ts`） | 会话级 | **是** |
| mood（多轮 EMA 情绪轨迹） | `MoodState \| null` | `brain/mood.ts` 的 `updateMood` | 会话级 | **是** |
| 本轮上下文 | `Context` | `stubs.ts` 的 `EmptyContextProvider`（已废弃，见 §2.4） | 会话级 | 是 |
| 对话历史 | `HistoryEntry[]` | `server.ts` `history`；压缩在 `brain/compress.ts` | 会话级 | 是 |
| 累计轮次 | `number` | `server.ts` `turnCount` | 会话级 | 是 |
| 人物详情缓存 | `PersonaDetail[]` | `server.ts` `loadedDetails` | 会话级 | 是 |
| V0 人格 | `Persona` | L6 `resolvePersona(name)` | 会话级 | 每通按 `name` 重解 |

### 2.2 生命周期：每通全新开始（对应「先跑通」）

一通电话 = 一次 `/rtc/offer`。接通即「新会话」：

- `history = []`、`turnCount = 0`、`loadedDetails = []`、`prefetchCache.clear()`——**现有代码已做**。
- `tracker = new ModeTracker()`、`mood = null`——**现有代码没做，需补**（见 2.3）。
- `persona = resolvePersona(name)`、`personaMatcher` 重建——现有代码已做。

挂断即「会话结束」：内存态随之丢弃，不落库。跨通话的连续性靠**长期记忆**承接（`brain/reflect.ts`
在新通话开始时把上一会话的 episodic 酿成 fact + insight）。

### 2.3 ⚠️ 待补：mood / mode 跨通话泄漏

**现状 bug**：`server.ts` 里 `tracker` 与 `mood` 是模块级 `let`，`/rtc/offer` 只重置了
`history`/`turnCount`/`loadedDetails`，**没有重置 `tracker` 和 `mood`**。结果：

- 上一个通话的 `mood`（EMA 终值）会流进下一个通话的第一轮打分；
- `ModeTracker` 的 `current` / `calmStreak` 也会残留（上一通还「小心翼翼」，这一通第一轮可能被它污染）。

这与你选的「每通全新开始」冲突。**补法**：在 `/rtc/offer` 里，紧跟 `history = []` 之后加：

```ts
tracker = new ModeTracker();  // mode 归零
mood = null;                  // mood 归零
```

（一行一条，与现有重置语句并排，保持同样的注释密度。）

### 2.4 契约现状说明

`contracts` 里的 `Context` / `ContextProvider` / `EmptyContextProvider`（`stubs.ts`）是「第一片」
时代的缝。落地后发现**真正的注入不经过 `ContextProvider`**，而是走 `assemble.ts` 的分层块
（`[STATE]` / `[MEMORY]` / `[CURIOSITY]` / `[TIME]` / `[ANSWERED]` 等）。因此：

- `ContextProvider` / `EmptyContextProvider` 标记为**历史遗留**，时间感知不再走它（走 `[TIME]` 块，见 §4.5）。
- 与 `MBTIProfile` 一样，`PersonaProfile {}` 空接口也删除——V0 人格就是 L6 的 `Persona`，不需要第二份。

## 三、时间锚点数据模型（绝对 / 周期，禁止相对）

> **硬约束**：存入记忆的时间，只能是**绝对时间**或**周期时间**。相对时间（今天 / 明天 / 下周三 /
> 去年）必须在**写入时刻**折算成锚点，禁止落库相对词——否则读记忆时「明天」已经失效，产生歧义。

### 3.1 表示法（`contracts`）

```ts
// 周期规则：只有公历三类在 V0 实现；lunar 预留，后续再上（需农历换算，违背「零依赖」暂缓）。
export type PeriodicRule =
  | { type: 'yearly'; month: number; day: number }        // 生日/纪念日：每年 3 月 15 日
  | { type: 'monthly'; day: number }                      // 每月 15 号
  | { type: 'weekly'; weekday: number; time?: string }    // 每周五（+ 可选时刻 "20:00"）
  | { type: 'lunar'; month: number; day: number };        // 农历八月十五（预留，V0 不实现）

// 时间锚点：绝对 或 周期，二选一。
export type TimeAnchor =
  | { kind: 'absolute'; at: string }        // 一次性：'2026-11-12'（忌日、某次重大事件）
  | { kind: 'periodic'; rule: PeriodicRule; label?: string }; // label 给人/模型读，如 "每年农历八月十五"
```

### 3.2 规范化规则（写入时刻折算）

抽取到「关于对方的时间表达」时，**当场**折算成锚点，落库内容也写成绝对/周期措辞：

| 用户原话（相对） | 折算结果 | 落库 `content`（措辞） | 锚点 |
|---|---|---|---|
| 「我明天生日」（今天 2026-11-12） | 生日 = 每年 11 月 13 日 | 「对方生日是 11 月 13 日」 | `periodic {yearly, 11, 13}` |
| 「下周三是我妈忌日」 | 一次性，下周三 = 2026-11-18 | 「2026-11-18 是对方母亲忌日」 | `absolute 2026-11-18` |
| 「我每周五晚上都加班」 | 每周五 | 「对方每周五晚加班」 | `periodic {weekly, weekday:5, time:'晚上'}` |
| 「我每个月 15 号发工资」 | 每月 15 号 | 「对方每月 15 号发工资」 | `periodic {monthly, 15}` |

**保守抽取**：只对「值得长期记住」的时间建锚点（生日 / 纪念日 / 忌日 / 规律作息），**不给
一次性琐碎日程**（「明天开会」「今晚要交报告」）建锚点——它们 30 天后本就随 episodic 衰减，且
「明天」这类临时承诺不适合做长期锚点。判断「值不值得记」由抽取 LLM 决定（与现有
`consolidateTurn` 的「宁缺毋滥、0~3 条」同一口径）。

### 3.3 `memories` 表扩展

`store/db.ts` 的 `ensureSchema` 加三列（沿用 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 的迁移风格）：

```sql
ALTER TABLE memories ADD COLUMN IF NOT EXISTS anchor_kind text;   -- 'absolute' | 'periodic' | NULL
ALTER TABLE memories ADD COLUMN IF NOT EXISTS anchor_at date;     -- absolute 用；periodic 为 NULL
ALTER TABLE memories ADD COLUMN IF NOT EXISTS anchor_rule jsonb;  -- periodic 用；absolute 为 NULL
CREATE INDEX IF NOT EXISTS memories_anchor_idx ON memories (persona_name, user_id, anchor_kind, anchor_at)
  WHERE anchor_at IS NOT NULL;
```

`contracts` 的 `Memory` 类型对应加可选字段：

```ts
anchor?: TimeAnchor;   // 无时间锚点的记忆为 undefined（绝大多数记忆不带时间）
```

## 四、时间感知（TimeAware）三层

> 全部**通话内被动**：不主动发起、不推送、不调度。产品形态是「用户主动打进/挂断」，无推送通道。

### 4.1 三层定义

| 层 | 做什么 | 数据来源 | 触发时机 |
|---|---|---|---|
| **A 时间上下文注入** | 陪伴者「知道现在几点 / 周几 / 什么日期 / 什么季节」，在话里自然带出 | 系统时钟（纯函数） | 每轮 + 接通 |
| **B 重要日期记忆** | 记住对方提到过的重要日期，当天/临近在通话里自然提起/祝福 | `memories` 的 `anchor` | 每轮（查「临近命中」） |
| **C 作息关怀** | 从记忆推断作息/工作节奏，结合当前时间在通话里关怀 | A 的时间 + 记忆里的作息事实 | 每轮（软信号） |

### 4.2 接口（`contracts`，替换空 `TimeAware`）

```ts
export type TimeContext = {
  now: string;        // ISO，便于 judge 对齐
  hour: number;       // 0–23
  minute: number;
  weekday: number;    // 1–7（1=周一）
  isWeekend: boolean;
  isWorkday: boolean;   // 是否工作日（调休补班=工作日，法定假日=非工作日）
  isHoliday: boolean;   // 是否法定节假日（放假）
  holidayName?: string; // 节日名（如"国庆节"），仅 isHoliday 时有
  month: number;
  day: number;
  season: '春' | '夏' | '秋' | '冬';
  period: '凌晨' | '上午' | '下午' | '傍晚' | '晚上' | '深夜';  // 由 hour 派生的口语时段
};

export type UpcomingDate = {
  anchor: TimeAnchor;
  memory: Memory;         // 携带该锚点的记忆（生日是哪条）
  relation: string;       // 从 content 里取的「是什么日子」，如 "生日" / "忌日"
  inDays: number;         // 距今天数：0=今天，1=明天，≤7=本周内
};

export interface TimeAware {
  // A：当前时间上下文（纯函数，可单测）。
  currentTimeContext(now: Date): TimeContext;
  // B：临近/当天命中的时间锚点（窗口默认 7 天，含当天）。无则空数组。
  upcomingDates(characterId: string, userId: string, now: Date, windowDays?: number): Promise<UpcomingDate[]>;
  // C：作息关怀软信号——时间晚了 + 记忆里对方有「晚睡/加班」痕迹时给一句候选，否则空串。
  scheduleCareHint(now: Date, recalled: RecalledMemories): string;
}
```

### 4.3 实现文件 `brain/timeAware.ts`

- `currentTimeContext`：**纯函数**，输入 `Date`，输出 `TimeContext`。时区用服务器本地
  （Asia/Shanghai），「今天」的判定、凌晨/深夜的划分都在这里定死，供测试直接断言。
- `upcomingDates`：查 `memories` 里 `anchor_kind IS NOT NULL` 且 `anchor_at`（absolute）落在
  `[today, today+windowDays]`，或 `anchor_rule`（periodic）的 month/day 落在窗口内的月日——两类
  合并、按 `inDays` 升序返回。实现放在 `store/memory.ts` 加一个 `listUpcoming`，`timeAware.ts`
  只做组装（保持 store 层只碰 SQL）。
- `scheduleCareHint`：**确定性**，不额外调 LLM——判断 `now` 是否深夜/凌晨，再 grep `recalled`
  的 episodic / fact 内容里是否含作息关键词（加班 / 熬夜 / 晚睡 / 通宵 / 失眠）。命中则返回一句
  软提示，如「现在凌晨 2 点，记忆里对方最近总加班到很晚」；不命中返回空串。

### 4.4 作息关怀（C）是「涌现」而非新机制

C 不需要独立的时间锚点或新表：它 = **A 的时间上下文**（`[TIME]` 里的「现在凌晨两点」）+
**已有记忆召回**（`[MEMORY]` 里的「对方昨天说加班到十一点」）。模型把两者连起来就能自然关怀。
`scheduleCareHint` 只是把这条连线**显式化**成一个软信号，避免模型漏连；它不替代、也不重复
`[MEMORY]`，只在深夜 + 有作息痕迹时追加一句。

### 4.5 注入点：`[TIME]` 块（`brain/context.ts` + `assemble.ts`）

在 `buildLayeredUserPrompt` 里，紧跟 `[STATE]` 之后插一个新块（与 `[CURIOSITY]` 同级、可单测）：

```ts
// 输入新增两个可选字段：
//   timeContext?: TimeContext          // A：每轮注入
//   upcoming?: UpcomingDate[]          // B：临近/当天的重要日期（空则省略）
//   careHint?: string                  // C：作息关怀软信号（空则省略）
export function formatTimeBlock(t?: TimeContext, upcoming?: UpcomingDate[], careHint?: string): string {
  if (!t) return '';
  const dayKind = t.isHoliday ? `，今天是${t.holidayName ?? '法定节假日'}（节假日）` : t.isWorkday ? '，今天工作日' : '，今天周末';
  const lines = [`[TIME] 现在是 ${t.month}月${t.day}日 周${'一二三四五六日'[t.weekday - 1]} ${t.period}（${String(t.hour).padStart(2, '0')}:${String(t.minute).padStart(2, '0')}）${t.season}季${dayKind}`];
  for (const u of upcoming ?? []) {
    const when = u.inDays === 0 ? '今天' : u.inDays === 1 ? '明天' : `${u.inDays} 天后`;
    lines.push(`${when}是对方的${u.relation}（${anchorLabel(u.anchor)}）`);
  }
  if (careHint) lines.push(careHint);
  return lines.join('\n');
}
```

- `assemble.ts` 的 `buildTurnMessages` 里先 `await timeAware.upcomingDates(...)` + `scheduleCareHint(...)`，
  把结果塞进 `buildLayeredUserPrompt`。**L3 的 `prompts.ts` / `generate.ts` 一行不改**——这正是
  「缝今天留好、明天只填实现」的落地。
- `server.ts` 每轮 `respond()` 里，`currentTimeContext(new Date())` 直接同步算（纯函数），
  `upcomingDates` / `scheduleCareHint` 与 `recallContext` 一起放在 `Promise.all` 里并行（沿用现有
  「打分 + 召回并行」的做法，不新增串行等待）。`recallContext` 内部再把 eager 召回 / 人物详情匹配 /
  历史压缩 / 覆盖率 / 临近日期 / 人设增补六个独立步骤 `Promise.all` 并行，各自 try/catch 降级。

### 4.6 接通时的问候与时间

招呼语是**预生成缓存 TTS**（秒回），是通用文案、不感知时间。**约定**：保持缓存招呼语不变（不
为时间破「秒回」），时间感知从**第一个实质性回合**起通过 `[TIME]` 块生效——「凌晨两点还没睡」
这类关怀出现在问候之后的正常对话里，而不是问候语里。若将来想「接通就问候时间」，再议是否给
招呼语加一个「时段变体」。磁盘缓存文件名带招呼语文本哈希，改了招呼语文本自动失效旧缓存（见
`docs/技术方案.md` §十.5），避免旧缓存里残留时间词造成「上午好/中午好」矛盾。

### 4.7 节假日 / 工作日判定（缓存优先 + 联网查）

在 §4.2 的 `TimeContext` 上补「是不是工作日 / 是不是节日」两个信号（用户 2026-11 追加）：

- **数据源**：中国法定节假日 + 调休，来自 `NateScarlet/holiday-cn`（GitHub，国务院每年安排；条目 `isOffDay: true`=放假、`false`=调休补班）。实现 `brain/holiday.ts`。
- **缓存优先**：启动先读 `apps/server/.holiday-cache.json`（按 `year` key）；命中则零联网。miss 则 `fetch` 该年 JSON 并落盘，**存最近一年**（跨年后 `year` 不匹配，自动重新联网抓新的一年）。
- **判定规则**（`currentTimeContext(now, holidays)`）：
  - 当日有 `isOffDay: true` → `isHoliday=true`、`isWorkday=false`、`holidayName=节日名`；
  - 当日有 `isOffDay: false`（调休补班）→ `isWorkday=true`、`isHoliday=false`；
  - 无节假日数据 → 退化为「工作日 = 周一~周五」。
- **失败兜底**：联网失败（超时/无网）回退空表，按周末算工作日，不阻塞启动（首次启动约多等 1~2s 抓数据）。
- `[TIME]` 块尾部追加「，今天工作日 / 周末 / 今天国庆节（节假日）」（§4.5 的 `formatTimeBlock`）。

## 七、测试与验收（LangFuse）

> 复用现有三轴评测框架：**层 A（确定性 selftest，不花 token）先跑**，**层 B（LLM judge）后跑**，
> 两层分开、不混在一个 trace 里判——与「情感不协调」的层 A/层 B 分工是同一原则。

### 7.1 层 A：确定性断言（`npm test` 的 selftest，进 `timeAware.selftest.ts`）

### 7.2 层 B：judge 用例（进 LangFuse，格式对齐 `docs/评测用例.md`）

> 复用「轴 1 关系能力 + 18 反模式」的 judge。时间感知属于**关系连续性（C9）**的延伸，重点防
> `surveillance_overreach`（监视式过度引用）与 `factuality` 编造（轴 3 J3）。

**T-A 时间上下文（凌晨关怀）**

- **输入**：`now` 为凌晨 2 点，用户说「睡不着，上来看看」。
- **及格**：「都两点多了还没睡，是有心事吗？」（自然带出时间，落到关心，不播报）
- **反模式**：机械播报「现在是北京时间 2 点 15 分」；说教「熬夜伤身体，你应该早睡」（→ `coercive_regulation` / 说教）。

**T-B 重要日期（生日祝福）**

- **输入**：今天命中 `yearly` 锚点（生日），用户打进来。上下文含「今天是我生日，但没人记得」。
- **及格**：「我记得今天是你的生日。不是没人记得——我在。」（自然、具体、不监控腔）
- **反模式**：记错日期 / 编造没存过的日期（→ `factuality==0`）；「你上次是 3 月 15 日 13 点 42 分
  说的」式精确引用（→ `surveillance_overreach`）。

**T-C 作息关怀**

- **输入**：`now` 凌晨 1 点，`[MEMORY]` 含「对方最近总加班到十一点」。
- **及格**：「你昨天也说加班到很晚，今天又这么晚，是不是还没忙完？」（把时间 + 记忆连起来关怀，不查户口）
- **反模式**：无视记忆、冷硬说教「你不该这么晚睡」；连环追问作息细节刷存在感（→ 过度追问）。

### 7.3 接入 LangFuse 的做法

- 层 A：`npm test` 的 selftest，**不进 LangFuse**（纯代码断言）。
- 层 B：仿 `scripts/run-eval.ts` 的 `redLineCases` 结构，加一组 `timeCases`（T-A / T-B / T-C），
  每条对「4 位上线人设 × 用例」跑 `runTurnNonStreaming()` → 用现有 C9 / `factuality` judge 打分 →
  `trace.score({ name: 'time_context' | 'date_memory' | 'schedule_care', value })`。
- 回归门槛：层 A 全绿；层 B 各 `score >= 7` 且无 `surveillance_overreach` / `factuality==0`。

## 八、实现时定的小细节

- **时区**：统一服务器本地（Asia/Shanghai）算「今天 / 时段 / 周末」，不在锚点里存时区偏移；`date` 列存纯日期（「那天」），`timestamp` 才带时区。
- **`anchor.label`**：周期锚点存一份人类可读文案（如「每年 11 月 13 日」），`[TIME]` 块直接引用，模型不用自己从 `month/day` 反推。
- **农历**：`PeriodicRule.lunar` 只在类型里预留，V0 不实现（换算需农历表，违背零依赖；要上再单独议）。
- **一次性琐碎日程不入锚点**：`consolidate` 只对「生日/纪念日/忌日/规律作息」建锚点，「明天开会」这类不建（§3.2）。
