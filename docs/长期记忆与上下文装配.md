说话链路现在的形态（热路径一条线，记忆读写甩到后台）：

```
planTurn（打分→情绪，不变）
  → assembleTurn（热路径：eager 召回 L2 + 分层装配，无工具循环）
  → streamMessages（流式出句 → 逐句 TTS）
  └─ 一轮结束后（异步，不进热路径）：
       consolidateTurn（抽取→分类→写记忆）  +  prefetchNextTurn（look-ahead 预取）
```

## 1. 热路径：上下文装配（`brain/assemble.ts`）

热路径零工具循环，保住实时语音的首字延迟：

1. **eager 召回**：`store.recall(userId, 本轮文字)` → 约束硬召回 + fact/preference/episodic 混合召回，
   注入 L2 `[MEMORY]`。召回失败降级为空记忆，不阻断对话。
2. **look-ahead 预取（可选）**：若 `prefetchCache` 有上一轮后台预热的命中，用 `mergeRecalled`
   把它们并入本轮召回（纯增量、按 id 去重，预算裁剪兜底）。
3. **人物详情渐进加载 + L5 压缩 + 分层装配**，产出完整 `messages` 直接交给 `streamMessages`
   流式生成最终回复。`messages` 是多轮结构：`system` + 逐字历史轮次（原生 `user`/`assistant`）
   + 最后一个 `user`（分层块 + 摘要 + 本轮文字）。**历史不再拍平成一段文本**——原生多轮让代词/
   指代绑定可靠得多（见 §4）。

   以上 eager 召回 / 人物详情匹配 / 历史压缩 / 覆盖率查询 / 临近日期 / 人设增补六个互不依赖的
   步骤在 `recallContext` 里 `Promise.all` 并行（各自 try/catch 降级），削掉串行 await 的延迟尖峰。
   装配时若上一轮以问句结尾，还注入 `[ANSWERED]` 块，防「已答过的问题被再问一遍」。

> 关键取舍：热路径里**只有一次向量召回，没有额外的 LLM 往返**。对比早期版本，去掉了「要不要
> 调工具」那次决策调用——那才是「多一次小调用」的元凶。

## 2. 后台记忆 Agent（`brain/consolidate.ts`）

把「写」和「定向召回」从实时回复里挪出来，异步、best-effort、失败只告警不阻断：

- **consolidateTurn（写）**：一轮结束后，从「她这一轮 + 我这一轮」里抽取值得长期记住的内容
  （0~3 条，宁缺毋滥），`classifyMemory` 确定性分类兜底后落库——对齐 Character.AI / Replika
  的「后台事实抽取」。
- **纠正即删**：抽取时若对方在纠正之前听错/记错的事实（「不是签证，是全栈」），顺带输出
  `retract`（错误关键词），`store.retract` 把含该词的活动 `fact/preference/episodic` 归档
  （superseded，不硬删），避免错误画像残留。关键词太短（<2 字）跳过，防误删。
- **prefetchNextTurn（look-ahead 预取）**：用上一轮文字预热下一轮可能用到的记忆，塞进
  `createPrefetchCache` 的单槽缓存，下一轮 `assembleTurn` 的 eager 召回会取走并并入。纯增量、
  推测性，猜偏只浪费一点后台算力，不伤热路径。
- **createPrefetchCache**：每 `characterId:userId` 单槽，`set` 覆盖、`take` 取走即清空
  （每次预取只服务「紧接着的下一轮」）。

> 为什么「读」不能全丢后台：当前这句回复的内容取决于「读到了什么」，后台异步读到也来不及喂
> 给这一轮。所以「读」仍同步做（但用廉价的向量召回，不是 LLM）；后台只能预热**下一轮**。
> 这是「异步救不了当前轮、只能救下一轮」的根本约束。

## 3. 长期记忆（五型）

- **类型**：`constraint`（硬规则/红线，无条件在场）、`fact`（稳定事实，`entity_id` 覆盖旧条）、
  `preference`（软偏好）、`episodic`（事件，软激活：30 天基础衰减 + 提及续命）、
  `profile`（人设：反思沉淀的身份/特质/高层洞察，**强制在场**；历史上曾叫 `insight`、后叫 `persona`，现统一为 `profile` 以区分于陪伴者 `Persona`）。
- **写入**：`consolidateTurn`（后台抽取）与 `reflect.ts`（后台反思）都会 `classifyMemory`
  （LLM temperature=0 确定性分类）兜底钉回正确桶，分类失败回退信任自报。
- **时间标注**：抽取出的内容若含「目前/正在/即将/现在/当前/最近」等状态性时间词，`tagRecordedAt`
  会在句尾追加「（记录于YYYY年M月D日）」，避免把瞬时状态当成永久事实；相对时间词（明天/下周三）则
  由 `rewriteRelativeTime` 折算成绝对日期。
- **召回**：constraint + profile 硬召回全量（强制在场）；其余三型 `dense`（pgvector 余弦）+ `lexical`（pg_trgm）RRF 融合。
- **存储**：`memories` 表（pgvector `vector(1024)`），表结构在 `store/db.ts` 的 `ensureSchema`。
- **隔离**：每条记忆挂 `persona_name`（=`persona.name`）＋ `user_id`，画像按人物完全隔离——程书衡
  不会读到只告诉沈知遥的事。所有 store 方法第一个参数是 `personaName`；后端反思（`reflect.ts` 的
  profile 沉淀）同样按人物隔离。

### 反思（记忆巩固，`brain/reflect.ts`）

- **触发**：新通话开始（`/rtc/offer`）异步跑一次，不阻塞建连；把上一会话积累的 episodic 退一步酿成 `fact`（稳定事实，entity 覆盖）+ `profile`（高层洞察）。
- **控量**：模型少而精（profile 0~5 条、去重）+ `store.prune` 硬上限（默认 20 条，归档最旧、不硬删）。
- **注入**：产物流进下一次 `recall` → L2 注入（profile 排约束之后、事实之前）。

## 4. 上下文分层（L0–L5）

| 层 | 内容 | 角色 | 处置 |
|---|---|---|---|
| L0 | system（人设 + 安全红线 + 记忆引导） | system | 固定成本 |
| L1 | `[STATE]` 状态快照（Turn/Mode/Stance/Emotion/心境） | user | 固定 |
| L2 | `[MEMORY]` 召回记忆（五型，约束子预算 ≤ 40%） | user | 预算裁剪 |
| L4 | `[REMINDER]` 安全红线尾播（首尾三明治） | user | 固定 |
| L5 | 历史对话 | **逐字轮次 = 原生 `user`/`assistant` 消息**；`[xxx SUMMARY]` 摘要 = 留在最后一条 user | **唯一压缩对象** |

> **多轮改造（指代修复）**：L5 的逐字轮次不再拍平成「对方：…/我：…」一段文本，而是发成原生
> `user`/`assistant` 消息；只有压缩摘要（无天然角色）与 `[MEMORY]`/`[STATE]` 等分层块一起留在
> 最后一条 `user` 里。原因：拍平成一段文本时，模型对「它/这个」这类代词的先行词绑定不可靠——
> 指代在上一句却搞不清；原生多轮消息的注意力天然追踪「谁何时说了什么」，指代解析可靠得多。
> 生成温度顺带从 0.7 降到 0.6（`brain/generate.ts` 的 `streamMessages`/`generateText`），减少
> 「有时」的抖动（次要杠杆，主因是消息结构）。

带内标记（`[STATE]` / `[MEMORY]` / `[CURIOSITY]` / `[TIME]` / `[ANSWERED]` / `[REMINDER]` / `[HISTORY SUMMARY]` …）既给模型分界、也给代码当回捞锚点。

## 5. 上下文压缩（`brain/compress.ts`，只压 L5）

按「历史超出预算的倍数」四级升级（kima 的 TOOL_COMPRESS 一级因 companion 无重工具日志而省略）：

| 倍数 | 级别 | 表现 |
|---|---|---|
| < 1 | NONE | 原样返回 |
| 1–1.5 | HISTORY_SUMMARY | 保留最近 6 轮，更早 LLM 摘要成 `[HISTORY SUMMARY]` |
| 1.5–2 | TOPIC_SUMMARY | 保留最近 4 轮 → `[TOPIC SUMMARY]` |
| ≥ 2 | EMERGENCY | 保留最近 2 轮 → `[EMERGENCY SUMMARY]` |

摘要走 `createSummarizer`（DeepSeek temperature=0）。压缩不变量：**至多一条摘要、恒在最前**。

## 7. 人物记忆渐进式加载

> 与 §3 的「用户长期记忆」是两回事：这里加载的是**陪伴者自己**的背景文件（`character/<姓名>/`）。

像 Claude Code 的记忆：常驻的是「目录」，详情一条一个文件、命中才加载。

| 层 | 文件 | 加载 | 注入位置 |
|---|---|---|---|
| 核心层 | `角色卡.md` | 常驻 | L0 system |
| 索引层 | `记忆.md`（标题+钩子+链接） | 常驻 | L0 system |
| 关系 | `关系.md` | 常驻 | L0 system |
| 详情层 | `认知/` `经历/` `偏好/`（frontmatter `description`=触发钩子） | **语义命中才加载** | `[PERSONA]` 块（user 消息） |

机制：`createPersonaMatcher` 预计算每条详情 `description` 的向量，每轮对用户话嵌入一次、余弦
超阈值（默认 0.5）即加载——对齐 Claude Code「用 description 决定 recall」。命中的详情进会话级
缓存（`loadedDetails`），本会话内不卸载，注入成 `[PERSONA]` 块。

**回退**：`character/<姓名>/` 不存在（如尚未写文件的角色）时，回退到 `persona/*.ts` 硬编码
`systemPrompt`、不启用渐进详情。
